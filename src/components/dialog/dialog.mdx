## Problem

Most modal dialogs are a `<div>` on top of the page with a dark overlay behind it. It looks modal. For anyone not using a mouse, it often isn't:

- **Focus escapes behind the overlay.** Nothing stops <kbd>Tab</kbd> from walking out of the dialog and into the page underneath. Keyboard users end up operating controls they cannot see, behind a dark overlay.
- **Focus is not returned on close.** When the dialog closes, focus drops to `<body>` and the keyboard user starts again from the top of the page instead of the button they pressed.
- **The background is still reachable by screen readers.** Even with a focus trap, screen reader users can read and activate the whole page behind the dialog in browse mode, because nothing marked it inert. The usual fix, `aria-hidden="true"` on every sibling of the portal, breaks when something else (a toast, a third-party widget) renders beside it.
- **No accessible name.** The overlay is announced as "dialog" with no title, or as nothing at all if it has no role, so the user does not know what just opened.
- **Esc ignored.** The APG's one universal way out is not wired up, or it closes the dialog but leaves the parent's state saying it is open.
- **Scroll bleeding through.** The wheel or a touch drag scrolls the page behind the dialog. When the page is locked with `overflow: hidden`, its scrollbar disappears and the layout jumps sideways.
- **z-index stacking bugs.** The overlay competes with sticky headers, dropdowns and toasts for the highest `z-index`, and loses inside a parent with `transform` or `overflow: hidden`. Portals fix the clipping and add their own problems.
- **A backdrop click closes it during a text drag.** Selecting text in the dialog and releasing the mouse just outside it counts as a click on the overlay, and the form the user was filling in vanishes.

## Solution

`Dialog.Content` renders a real `<dialog>` and opens it with `showModal()`. Most of the list above is solved by the browser, not by JavaScript in Keyline:

- **The top layer, not z-index.** A modal `<dialog>` is rendered in the browser's top layer, above every `z-index` and outside every `overflow` and `transform`. It never loses a stacking fight, so it needs no portal: it can be rendered wherever it is written, and context, CSS inheritance and event bubbling keep working.
- **A truly inert background.** While a modal dialog is open, the browser makes everything outside it inert: it cannot be focused, clicked, or found by assistive technology in browse mode. Keyline sets no `aria-hidden` on siblings and keeps no list of what to hide, so nothing breaks when other content renders next to the dialog.
- **Focus kept inside by the platform.** Because the page is inert, <kbd>Tab</kbd> and <kbd>Shift</kbd> + <kbd>Tab</kbd> never reach anything behind the dialog. Keyline does not ship a focus trap for it.
- **Esc from the platform, state from React.** The browser turns <kbd>Esc</kbd> into a `cancel` event on the topmost dialog only, so nested dialogs close one at a time. Keyline calls `preventDefault()` on it and calls `onOpenChange(false)`, so the state decides: a controlled parent that keeps `open` true keeps the dialog open. If the browser closes the dialog anyway (Chromium does on a second <kbd>Esc</kbd> without other user input in between), the `close` event reports it and Keyline reopens the dialog if the parent still says `open`.

Keyline adds what the platform leaves to the page:

- **Initial focus.** On open, focus goes to `initialFocus` if you pass a ref, else to the first tabbable element inside (skipping `tabindex="-1"`, which Chromium's own choice would take), else to the dialog itself.
- **Focus return.** On close, focus goes back to whatever had it before the dialog opened, usually the trigger. If that element is gone (the trigger was unmounted while the dialog was open), it tries the trigger, and otherwise leaves focus where the browser puts it, without throwing.
- **A name and a description.** `Dialog.Title` (an `h2` by default; use `as` for another level) and `Dialog.Description` are wired to `aria-labelledby` and `aria-describedby` automatically. In development, `Dialog.Content` warns if it has neither a title nor an `aria-label`. `role="alertdialog"` is available for urgent confirmations.
- **Backdrop clicks that mean it.** A click closes the dialog only if the pointer went down _and_ up on the backdrop. Dragging a selection out of the dialog, or pressing on the backdrop and releasing inside, does nothing. Turn it off with `closeOnBackdropClick={false}`; alert dialogs never close this way.
- **Scroll lock without a jump.** While any Keyline dialog is open, the root element gets `overflow: hidden`, and `scrollbar-gutter: stable` if the page had a classic scrollbar, so the layout does not shift sideways. The lock holds until the last nested dialog closes.
- **Motion that respects the user.** Enter and exit are CSS transitions using `@starting-style` and `transition-behavior: allow-discrete`, timed by `--kl-duration-base`, so they are instant under `prefers-reduced-motion: reduce`.
- **Controlled or uncontrolled.** Pass `open` + `onOpenChange`, or `defaultOpen`.

## Props

`Dialog.Root` renders no element. `Dialog.Trigger` and `Dialog.Close` render `<button type="button">`; `Dialog.Content` renders `<dialog>`; `Dialog.Title` renders a heading; `Dialog.Description` renders a `<p>`. Each part passes other props (`className`, `style`, `aria-*`, `data-*`, event handlers, `ref`) to its element. An `onClick` that calls `event.preventDefault()` on the trigger or a close button cancels the open or close.

Styling hooks: `data-state="open" | "closed"` on the trigger and the content, plus the native `[open]` attribute and `::backdrop`.

| Part             | Prop                   | Type                        | Default                                 |
| ---------------- | ---------------------- | --------------------------- | --------------------------------------- |
| `Dialog.Content` | `role`                 | `'dialog' \| 'alertdialog'` | `'dialog'`                              |
| `Dialog.Content` | `closeOnBackdropClick` | `boolean`                   | `true` (always `false` for alertdialog) |
| `Dialog.Content` | `initialFocus`         | `RefObject<HTMLElement>`    | first tabbable, else dialog             |
| `Dialog.Title`   | `as`                   | `'h1'` … `'h6'`             | `'h2'`                                  |

## Keyboard

| Key                                 | Action                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| <kbd>Enter</kbd> / <kbd>Space</kbd> | On the trigger: opens the dialog and moves focus inside.                       |
| <kbd>Tab</kbd>                      | Next focusable element inside the dialog. Never reaches the page behind.       |
| <kbd>Shift</kbd> + <kbd>Tab</kbd>   | Previous focusable element inside the dialog.                                  |
| <kbd>Esc</kbd>                      | Asks to close the topmost dialog. Focus returns to the element that opened it. |

## Screen reader output

What the [Guidepup virtual screen reader](https://www.guidepup.dev/docs/virtual) announces, asserted in `dialog.screen-reader.test.tsx`:

| Moment                          | Announcement                                                         |
| ------------------------------- | -------------------------------------------------------------------- |
| The trigger                     | "button, Delete project, not expanded, has popup dialog"             |
| Reading on past a closed dialog | Nothing: closed dialog content is not in the accessibility tree      |
| Opening a dialog                | "dialog, Delete “Atlas”?, This removes the project and its history." |
| Opening an alert dialog         | "alertdialog, Delete “Atlas”?, …", and "assertive: Delete “Atlas”?"  |
| Next item in the dialog         | "heading, Delete “Atlas”?, level 2"                                  |

The virtual screen reader runs in jsdom, which has no top layer and no inert background. That the page behind a modal dialog cannot be reached is checked in real browsers by Playwright (focus and clicks). Real screen readers announce the dialog's name and role when focus moves into it, together with the focused control; the order and wording vary by screen reader and have not been checked by hand yet (see the manual checklist).

### Manual checklist (Orca + Firefox, TalkBack + Chrome)

Run against the [Keyboard test fixture](?path=/story/components-dialog--keyboard-fixture) story and record results in `docs/manual-testing.md`.

1. Tab to "Open form". Expect a button that says it opens a dialog (Orca: "has popup"; TalkBack may not say it).
2. Press <kbd>Enter</kbd>. Expect "Form dialog", dialog, and focus on the "Name" field.
3. Browse mode (Orca: arrow keys, including past the end; TalkBack: swipe left and right). Expect never to reach "Before", "After" or anything else behind the dialog.
4. Press <kbd>Esc</kbd>. Expect the dialog to close and "Open form" to be announced again.
5. Open the form, then "Open nested", then press <kbd>Esc</kbd>. Expect only the nested dialog to close and focus on "Open nested".
6. Open "Open text-only". Expect the alert's text to be read, with focus on the dialog itself.
7. TalkBack: open the form and use the back gesture. Expect it to close the dialog (it sends Esc) and return to "Open form".
8. Visual: the dialog surface, its border and the backdrop are clear in both light and dark themes.

## Known limitations

- **Tab does not wrap directly.** Browsers keep focus out of the page behind a modal dialog, but after its last control <kbd>Tab</kbd> goes to the browser's own toolbar before returning to the first control. The APG describes direct wrapping; Keyline follows the platform rather than adding a focus trap on top of it.
- **Content stays mounted while closed.** The `<dialog>` and its children are always rendered (hidden by the browser) so the exit transition can play. Effects inside run even while it is closed; render them conditionally on `open` if that matters.
- **No exit animation in Firefox.** Firefox (157 at the time of writing) does not support transitioning `overlay`, so the dialog leaves the top layer as soon as it closes. Chromium animates both ways; both animate the entry.
- **Modal only.** Non-modal dialogs (`show()`) and drawers are not covered yet.
- **Scroll lock is on the root element.** Pages that scroll an inner container instead of the document need to lock that container themselves.
- **Real Windows High Contrast has not been checked by hand,** only emulated.
