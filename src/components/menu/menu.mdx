## Problem

A menu looks like a button with a box of links under it, and that is how most are built. Then the keyboard and the screen reader find out:

- **A `<div>` that opens on click, with links inside and no roles.** Nothing says the button opens anything, and nothing says what opened. A screen reader hears "link, Copy, link, Paste" somewhere later on the page, if it finds them at all.
- **Arrow keys not implemented, so every item is a tab stop.** The user has to <kbd>Tab</kbd> through every item to get past the menu, and screen readers that switch to application mode inside `role="menu"` (as the role tells them to) press <kbd>↓</kbd> and get nothing.
- **Focus not moved into the menu, or not returned.** The menu opens but focus stays on the button, so the keyboard user is still behind it. Or it closes and focus drops to `<body>`, and they start again from the top of the page.
- **<kbd>Esc</kbd> ignored.** The one universal way out of a popup does nothing, or it closes the menu and also closes the dialog the menu was in.
- **Clipped or lost.** A menu inside a card with `overflow: hidden` is cut off at the card's edge. A menu portalled to `<body>` escapes the clipping but lands outside a modal dialog, where the browser makes it inert: it shows, and nothing in it can be clicked or focused.
- **`role="menu"` for site navigation.** A header "menu" of links given `role="menu"` and `role="menuitem"` stops screen readers from treating them as links: no link list, no "visited", and arrow keys the page never handles. **Navigation links are not a menu.** Use a `<nav>` with a list of links, and a disclosure button if it needs to collapse.
- **Checked state shown by an icon only.** A tick drawn next to "Show ruler" with no `aria-checked` is invisible to screen readers, and a tick drawn in colour alone disappears in forced-colours mode.

## Solution

`Menu.Trigger` is a `<button>` that says what it opens, and `Menu.Content` is a `role="menu"` that the browser shows as a native popover anchored to the trigger.

- **Roles, names and state from the APG.** The trigger has `aria-haspopup="menu"`, `aria-expanded`, and `aria-controls` while the menu is open. The menu is labelled by the trigger, so it is announced as "Edit, menu". Items are `menuitem`, `menuitemcheckbox` or `menuitemradio`, checkable items carry `aria-checked`, groups are `role="group"` named by their `Menu.Label`, and separators are `role="separator"`.
- **One tab stop, arrow keys inside.** Items are focused by script only (`tabIndex={-1}`), with roving DOM focus rather than `aria-activedescendant`, so every screen reader follows focus without extra support. <kbd>↓</kbd> and <kbd>↑</kbd> move with wrap, <kbd>Home</kbd> and <kbd>End</kbd> jump to the ends, and typing jumps to the next item that starts with what was typed. <kbd>Tab</kbd> closes the menu and lets focus move on.
- **Focus moved in and back.** <kbd>Enter</kbd>, <kbd>Space</kbd> or <kbd>↓</kbd> on the trigger opens the menu on the first item; <kbd>↑</kbd> opens it on the last. Choosing an item, or <kbd>Esc</kbd>, closes the menu and puts focus back on the trigger.
- **<kbd>Esc</kbd> closes only the menu.** Keyline handles <kbd>Esc</kbd> on the menu itself, which also stops the browser's own close request, so a menu inside a Keyline Dialog closes without closing the dialog. A second <kbd>Esc</kbd> closes the dialog.
- **The top layer, without a portal.** The menu is a native popover (`popover="auto"`, `showPopover()`), so it renders above everything, outside every `overflow` and `transform`, with no `z-index`. It stays where it is written in the DOM, so inside a modal dialog it is part of the dialog and not inert. The browser closes it on a click outside, and React state follows: `onOpenChange(false)` is called, and a controlled parent that keeps `open` true gets it shown again.
- **Placed by CSS, mirrored in RTL.** CSS anchor positioning puts the menu under the trigger, lined up with its inline start edge (the right edge under `dir="rtl"`), and `position-try-fallbacks` flips it above or to the other edge when there is no room. Where anchor positioning is missing, a small measured placement does the same and follows scroll and resize.
- **Checked state by shape and weight.** Checkbox items show a tick and radio items a dot, in a fixed gutter at the inline start, and checked labels are set in weight 500. The marks are drawn with borders, so forced-colours mode keeps them, and `aria-checked` carries the state to assistive technology.
- **Disabled items stay focusable.** A disabled item has `aria-disabled="true"`, is reached by the arrow keys and typeahead, is announced as unavailable, and does nothing when activated. The APG recommends this for menus, because a menu is a short list read one item at a time: an item that silently disappears from the arrow-key order leaves the user unsure the command exists at all. Tabs make the other choice (disabled tabs are skipped), because a tab list is a navigation row whose disabled entries are still read in browse mode.

## Props

`Menu.Root` renders no element. `Menu.Trigger` renders `<button type="button">`; `Menu.Content` a `<div role="menu" popover="auto">`; items, groups, labels and separators render `<div>`s. Each part passes other props (`className`, `style`, `aria-*`, `data-*`, event handlers, `ref`) to its element. An `onClick` on the trigger or an item that calls `event.preventDefault()` cancels the open or the activation.

`Menu.CheckboxItem` and `Menu.RadioGroup` are controlled only: what they show is app state that already lives outside the menu. A `Menu.Label` inside a `Menu.Group` or `Menu.RadioGroup` names that group.

Styling hooks: `data-state="open" | "closed"` on the trigger and the menu, `:popover-open` on the open menu, and `aria-checked` and `aria-disabled` on items.

## Keyboard

| Key                                 | Action                                                                                                |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| <kbd>Enter</kbd> / <kbd>Space</kbd> | On the trigger: opens the menu on the first item. On an item: activates it.                           |
| <kbd>↓</kbd>                        | On the trigger: opens on the first item. In the menu: next item, wrapping, disabled included.         |
| <kbd>↑</kbd>                        | On the trigger: opens on the last item. In the menu: previous item, wrapping.                         |
| <kbd>Home</kbd> / <kbd>End</kbd>    | First / last item.                                                                                    |
| A printable character               | Next item starting with the typed text. Repeat one letter to cycle; <kbd>Space</kbd> counts mid-word. |
| <kbd>Esc</kbd>                      | Closes the menu and returns focus to the trigger. Does not close a dialog the menu is in.             |
| <kbd>Tab</kbd>                      | Closes the menu and moves focus to the next control after the trigger.                                |

Activating a plain item closes the menu unless its `onSelect` calls `event.preventDefault()`. Checkbox and radio items keep it open. Moving the pointer over an item focuses it.

| <kbd>Esc</kbd>                    | "button, Actions, not expanded, has popup menu"                 |
| Reading on past a closed menu     | Nothing: closed menu content is not in the accessibility tree   |

The virtual screen reader counts positions among items of the same role, and starts a new count after a separator; real screen readers differ (most count every item in the menu). It reads a separator's implicit range ("max value 100, min value 0"), which real screen readers do not. The order and wording of announcements in Orca and TalkBack have not been checked by hand yet (see the checklist).

### Manual checklist (Orca + Firefox, TalkBack + Chrome)

Run against the [Keyboard test fixture](?path=/story/components-menu--keyboard-fixture) story and record results in `docs/manual-testing.md`.

## Known limitations

- **No submenus.** Items cannot open nested menus yet, so <kbd>→</kbd> and <kbd>←</kbd> do nothing inside the menu.
- **No context menus.** The menu opens from a button only, not from a right-click or the context-menu key.
- **No menubar.** A horizontal, always-visible `role="menubar"` is a separate pattern and is not covered.
- **No press-drag-release selection.** Pressing on the trigger, dragging to an item and releasing does not choose it; click the trigger, then the item.
- **Shortcuts are text only.** `shortcut` shows and announces the keys but does not listen for them.
- **Checkbox and radio items are controlled only.** Keep their state in your component.
- **Content stays mounted while closed,** so the exit transition can play. Effects inside items run even while the menu is closed.
- **Real Windows High Contrast has not been checked by hand,** only emulated.
